# תוכנית שדרוג · סריקה מלאה של כמה תיבות, ושיוך לחברות שלומד

תשובה לשני האפיונים מ-2026-11-10: "סריקת חשבוניות וקבלות ממספר חשבונות מייל" ו"מודול ניהול חברות, מסמכים ולמידת שיוך".
לא נכתב קוד לשני האפיונים עד אישור התוכנית. השדרוג נבנה בתוך המערכת הקיימת, בלי מערכת כפולה.

## מה קיים היום (נבדק בקוד ובמסד)

### סריקה
- **כמה תיבות:** כל תיבה מחוברת היא שורה ב-`fin_mailboxes`, עם תקופה משלה (`sync_from`), סטטוס, תאריך סריקה אחרונה, שגיאה ומונה מסמכים.
- **מה כבר נבנה:**
  - סריקה לאחור בחלונות של חודש, עם עמודים מלאים עד 2,500 מיילים בחודש.
  - "כבר נסרק?" נשמר לכל מייל (`fin_mail_seen`).
  - חלון התקדמות ועלות.
  - ZIP, Word, Excel ו-TIFF, וגוף המייל כמסמך.
  - SHA-256 וחשד לכפול לפי ספק, מספר וסכום.
- **החסר המרכזי: אין "מקטע" עם סטטוס, נקודת המשך ובקרת שלמות.**
  - מייל שנכשל לא נרשם ככישלון: הוא פשוט לא מסומן "נסרק" ומנוסה שוב.
  - לכן אי אפשר להבדיל בין "לא נמצא" ל"לא נבדק".
  - אין דוח סיכום.
- **המנוע רץ רק בשני מקרים:** כשחלון הסריקה פתוח, או בריצה הלילית (ב-Vercel Hobby יש cron יומי בלבד).
- **בפרודקשן:** `pg_cron` ו-`pg_net` מותקנים, ולכן אפשר להפעיל את המנוע כל דקה מתוך המסד, בלי שרת נוסף ובלי עלות.
- **אחסון:** 943MB מתוך 100GB (התוכנית שודרגה), כך שסריקה של שנים אחורה לא חסומה.

### שיוך לחברות
- **מה קיים כבר** (`server/finance/assign.js`), לפי סדר חוזק:
  1. ח.פ. של הנמען במסמך: התאמה מדויקת, 1.0.
  2. כללי נמען.
  3. כללי שולח וספק.
  4. **היסטוריה:** מסמכים מאושרים, ומסמכים ששויכו ביד (`business_source = manual`), כלומר תיקון של אדם כבר מלמד.
  5. שם וכתובת הנמען במסמך.
  6. ברירת מחדל של הספק.
  7. תיבת המייל, כהצעה בלבד.
- **סתירה בין סימנים חזקים** עוברת לבדיקה, ולא מוכרעת בשקט.
- **במסכים:** כרטיסי חברות, עמוד חברה עם המסמכים שלה, פילטר "לא משויך", וכללים במסך "כללים ואוטומציה".
- **החסר:**
  - תיבה משותפת לכמה חברות. היום לתיבה יש חברה אחת.
  - ספי ביטחון לשיוך שאפשר להגדיר, באחוזים של האפיון (95 / 75).
  - מסך ייעודי "מסמכים ללא שיוך", עם המלצה ושיוך קבוצתי.
  - היסטוריית שיוכים מפורשת לכל מסמך.
  - זיהוי חברה חדשה מתוך מסמך.
  - שמות חלופיים לחברה.
  - שמירת נמען המסמך (שם וח.פ.) בשדות נפרדים מהחברה שהמסמך שייך לה.

## שינויים במסד (`supabase/finance.sql`, אידמפוטנטי, עם RLS כמו שאר הטבלאות)

```sql
-- סריקה: מקטעים עם סטטוס ונקודת המשך
create table fin_scan_jobs (id uuid pk, mailbox_id uuid → fin_mailboxes, mode text check (mode in ('history','completeness')),
  date_from date, date_to date, tz text default 'Asia/Jerusalem', include_sent bool default false, status text
  check (status in ('queued','running','paused','done','incomplete','failed')), requested_by uuid, created_at, finished_at,
  report jsonb)                                   -- דוח הסיכום בסוף
create table fin_scan_segments (id uuid pk, job_id uuid → fin_scan_jobs, day_from timestamptz, day_to timestamptz,
  status text check (status in ('pending','running','done','failed','retry')), page_token text, listed int, processed int,
  failed int, attachments int, last_message_id text, last_message_at timestamptz, attempts int, error text, updated_at)
create table fin_scan_items (segment_id uuid, mailbox_id uuid, message_id text, status text check (status in
  ('done','failed','unreadable')), error text, files int, kept int, skipped int, at timestamptz,
  primary key (mailbox_id, message_id))           -- כל מייל: מה קרה לו. מחליף בהדרגה את fin_mail_seen

-- כפילויות בין תיבות: מסמך אחד, כל המקורות שלו
create table fin_document_sources (document_id uuid → fin_documents, mailbox_id uuid, message_id text, email_from text,
  email_subject text, email_date timestamptz, file_name text, at timestamptz, primary key (document_id, mailbox_id, message_id))
alter table fin_documents add column if not exists supersedes uuid, add column if not exists superseded_by uuid,  -- חשבונית מתוקנת
  add column if not exists recipient_name text, add column if not exists recipient_reg text,                   -- נמען, בנפרד מהשיוך
  add column if not exists assign_confidence numeric, add column if not exists assign_reason text

-- שיוך לחברות
create table fin_mailbox_businesses (mailbox_id uuid, business_id uuid, primary key (mailbox_id, business_id))  -- תיבה משותפת
alter table fin_businesses add column if not exists aliases text[] default '{}'          -- שמות חלופיים
create table fin_assignment_history (id uuid pk, document_id uuid, from_business uuid, to_business uuid,
  source text check (source in ('auto','suggestion_accepted','manual','bulk','rule')), confidence numeric, reason text,
  by uuid, at timestamptz)                       -- לא נמחק ולא נדרס
create table fin_company_candidates (id uuid pk, name text, reg_number text, address text, seen_in int, first_doc uuid,
  status text check (status in ('new','added','dismissed')), at timestamptz)  -- "נמצאה חברה חדשה במסמכים"
-- הגדרות: assign_auto (0.95), assign_suggest (0.75) ב-fin_settings
```
- **טוקני המייל:** עוברים להצפנה ב-Supabase Vault, שמותקן בפרודקשן. כך גם האבטחה מהתוכנית הקודמת נסגרת.

## מנוע הסריקה (מצב 1: היסטורית; מצב 2: שוטף)
1. **פתיחת סריקה:**
   - בחירת תאריכים ואזור זמן, ברירת מחדל ישראל.
   - אופציות: 30 יום / 3 חודשים / חצי שנה / שנה / 3 שנים / 5 שנים / כל ההיסטוריה (מהמייל הראשון שהספק מחזיר) / ידני.
   - נוצר job, והתקופה מתחלקת **למקטעים של שבוע**.
2. **עבודה ברקע:**
   - `pg_cron` קורא כל דקה ל-`action=scan-tick` עם מפתח סודי, שנשמר ב-Vault.
   - כל קריאה מטפלת במקטעים לפי התור במשך עד 45 שניות.
   - תיבות שונות רצות זו לצד זו, בתורות.
   - החלון בממשק רק מציג התקדמות ולא מריץ את הסריקה.
3. **בתוך מקטע:**
   - עוברים על **כל** העמודים, בלי תקרה.
   - `page_token` ו-`last_message_id` נשמרים אחרי כל עמוד ואחרי כל מייל, כך שעצירה ממשיכה מאותה נקודה.
   - כל מייל נרשם ב-`fin_scan_items` כ-done, failed או unreadable, עם הסיבה.
4. **בקרת שלמות בסוף מקטע:**
   - **ספירה חוזרת אצל הספק:** Gmail `resultSizeEstimate` או ספירה מלאה ב-Graph.
   - **השוואה ל-`fin_scan_items`:** כל מזהה שנשלף חייב להופיע עם סטטוס.
   - **קבצים:** אף קובץ לא נשאר בלי תוצאה.
   - **סטטוס:** מקטע עם failed או unreadable שלא טופל מקבל "דורש סריקה חוזרת" ולא "הושלם".
5. **ניסיונות חוזרים:**
   - מייל שנכשל ננסה שוב 3 פעמים, בהפרש 15 דקות, שעה ו-4 שעות.
   - 429 ו-5xx מהספק: המתנה לפי `Retry-After` והאטה של התיבה הזו בלבד.
6. **סריקת השלמה:**
   - אחרי שההיסטוריה הסתיימה, עוד מעבר על כל התקופה שמשווה רק מזהים, בלי לקרוא מחדש.
   - מעבר כזה רץ גם פעם בשבוע על 60 הימים האחרונים, כדי לתפוס מיילים שהגיעו באיחור.
7. **"הסריקה הושלמה"** מוצג רק אם כל המקטעים עברו בקרת שלמות. אחרת: "הסריקה אינה מלאה", עם רשימת ההודעות שלא עובדו וכפתור "נסה שוב".
8. **שוטף:** אותו מנוע עם מקטע "מאז הסריקה האחרונה", כל 15 דקות. הוא מחליף את הריצה הלילית, שנשארת כגיבוי.
   - **Gmail push (Pub/Sub):** דורש פרויקט Google Cloud עם Pub/Sub, ונשאר שלב אחר כך.
9. **קישורים להורדת חשבונית מתוך המייל:**
   - **מדיניות:** רשימה סגורה של דומיינים של ספקים מוכרים, שאתה מאשר.
   - **רק HTTPS,** בלי התחברות ובלי טפסים.
   - **מגבלות:** 10MB, ורק סוגי קבצים מאושרים.
   - **כל השאר:** נרשם כ"נמצא קישור, לא הורד".
10. **שרשורים:**
    - **קיבוץ:** מסמכים מאותו שרשור (`threadId` ב-Gmail, `conversationId` ב-Outlook) עם אותו ספק ומספר, או "מתוקנת" או "מבטלת".
    - **סימון:** `supersedes` / `superseded_by`. שום דבר לא נמחק.
11. **כפילות בין תיבות:** אם המסמך כבר קיים, לפי SHA-256 או לפי ספק + מספר + תאריך + סכום, נוסף רק מקור ב-`fin_document_sources`. מסמכים שונים לא מאוחדים רק בגלל אותו סכום או אותו ספק.
12. **יוצאות:** מושבתות כברירת מחדל, ונפתחות בהגדרה לכל תיבה. כך גם חשבוניות שהעסק שלח לא יוחמצו, אם רוצים אותן.

## שיוך לחברות שלומד
- **ציון לכל חברה מהסימנים הקיימים, ועוד:**
  - **תיבה משותפת:** סימן חלש, שאף פעם לא מספיק לבד.
  - **שמות חלופיים.**
  - **סתירה בין התיבה לנמען במסמך:** הנמען במסמך גובר, והמסמך עובר לבדיקה.
- **ספים:**
  - 95% ומעלה: שיוך אוטומטי. בפועל רק עם ח.פ. מדויק או כלל מפורש, ובלי סתירה.
  - 75%–94%: המלצה, עם החברה המוצעת והסיבה.
  - מתחת ל-75%: "ממתינים לשיוך".
- **למידה מכל פעולה:**
  - כל שיוך, תיקון, העברה, אישור המלצה או שיוך קבוצתי נכתב ל-`fin_assignment_history`.
  - ההיסטוריה משמשת מיד כסימן (בלי אימון מודל).
  - אחרי 3 החלטות זהות לאותו ספק, המערכת מציעה ליצור כלל קבוע. הכלל לא נוצר לבד.
- **מודל AI:** רק למקרה מורכב, כשאין סימן חזק. ומשתמשים במודל הזול.
- **הספק ≠ הנמען ≠ החברה:**
  - הספק נשמר ב-`supplier_*`.
  - הנמען כפי שהודפס נשמר ב-`recipient_*`.
  - החברה שהמסמך שייך לה נשמרת ב-`business_id`.
  - שם הספק אף פעם לא משמש לשיוך החברה.

## מסכים
1. **"ניהול מסמכים"** (המסך הקיים "כל המסמכים", משודרג):
   - לשונית "כלל המסמכים", בתצוגת רשימה, טבלה או כרטיסים, עם העמודות מהאפיון.
   - פילטר לפי תיבת מייל וסטטוס שיוך.
   - לשונית "החברות שלי": כרטיסי חברה עם הלוגו, ח.פ., מספר מסמכים, הסכום, מספר הממתינים לשיוך, התיבות המקושרות ועדכון אחרון.
2. **עמוד חברה:**
   - ראש העמוד: הנתונים מהאפיון.
   - המאגר של החברה, בתצוגת רשימה וטבלה.
   - בורר חברות בראש העמוד, כדי לעבור בין חברות בלי לחזור.
   - לשונית "הגדרות AI": תיבות, ספקים מזוהים, שמות ומספרים שנלמדו, כללים (עריכה ומחיקה), שיוכים אוטומטיים ותיקונים.
3. **"מסמכים ללא שיוך":**
   - לכל מסמך: תצוגה מקדימה, ספק, סכום, תאריך, תיבה, המלצה ואחוז ביטחון.
   - פעולות: אישור, חברה אחרת, השארה, "לא רלוונטי".
   - בחירה מרובה ושיוך קבוצתי.
4. **"ניהול סריקות":**
   - **כרטיס לכל תיבה:** תקופה, אחוז, נבדקו, חשבוניות, קבלות, נפסלו, דורשות בדיקה, שגיאות, תאריך אחרון.
   - **כפתורים:** התחל, עצור, המשך, סרוק מחדש, שנה תקופה, הצג מסמכים, הצג הודעות שלא עובדו.
   - **בראש המסך:** לוח מרוכז לכל התיבות.
   - **דוח סיכום בסוף כל סריקה,** כמו בדוגמה באפיון.
5. **חיבור תיבה חדשה:**
   - **בסיום החיבור:** בחירת תקופה ובחירת החברות שהתיבה משרתת (אחת, כמה, או "משותפת").
   - **בלי השפעה** על תיבות שכבר נסרקו.
6. **"נמצאה חברה חדשה במסמכים":** הודעה עם הצעה להוסיף חברה. לא נוצרת חברה בלי אישור.

## בדיקות (קריטריוני הקבלה)
כל 25 התרחישים משני האפיונים ייכנסו ל-`run.mjs`, מול מייל מדומה שמתנהג כמו Gmail ו-Graph:
- **עמודים:** 50,000 הודעות מדומות, עם עמודים של 500 ובלי תקרה.
- **עצירה והמשך:** עצירה באמצע והמשך מאותה נקודה, עם המזהה האחרון.
- **שתי תיבות ושגיאות:** שתי תיבות במקביל, 429 ו-503 עם ניסיון חוזר, וקובץ פגום שנרשם "unreadable".
- **סוגי מסמכים:** חשבונית בגוף המייל, קבלה בתמונה, חשבונית באנגלית.
- **כפילות:** אותה חשבונית בשתי תיבות נשמרת פעם אחת, עם שני מקורות.
- **שרשור:** חשבונית מתוקנת בשרשור מסומנת, והקודמת לא נמחקת.
- **סריקת השלמה:** מוצאת מייל שהוחמץ בכוונה.
- **סינון:** הצעת מחיר ופרסומת לא נכנסות.
- **10 תרחישי השיוך,** כולל תיבה משותפת, ח.פ. של חברה אחרת, ספק של שתי חברות, למידה מתיקון, חברה חדשה, והיסטוריית העברה.

**דיוק אמיתי (Recall / Precision):**
- נמדד רק על מאגר מתויג מהמייל שלכם, כמו בשלב 0 של התוכנית הקודמת.
- במערכת ייבנה מסך "בדיקת איכות" לתיוג מדגם.

2. **כפילויות בין תיבות ומקורות.**
3. **הצפנת טוקנים ב-Vault.**
4. **שיוך:**

   - "החברות שלי", עמוד חברה והגדרות AI.

5. **שרשורים וחשבונית מתוקנת.**
