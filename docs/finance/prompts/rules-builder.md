## הקשר משותף (להדביק בתחילת כל פרומפט)

```
אתה עובד על KURKOOS FINANCE AI, המערכת הפנימית של קבוצת קורקוס לאיסוף חשבוניות, בריפו kurkoos-group.
לפני כל שינוי קרא: docs/finance/README.md, supabase/finance.sql (החלקים של fin_rules, fin_rule_hits, fin_documents_guard,
fin_documents_relations), server/finance/assign.js, server/finance/pipeline.js, src/pages/finance/Automations.jsx,
src/pages/finance/ui.jsx, src/pages/finance/finance.css, ואת צילומי המסך ב-docs/finance/prompts/wellybox/.

כללים שאסור לשבור:
- זו הרחבה של מנוע הכללים הקיים (fin_rules + assign.js), לא מערכת חדשה ולא רכיב מנותק.
- הכללים לא מאשרים מסמכים ולא משנים מסמך מאושר או מיוצא (status approved/sent). זה נאכף גם במסד.
- מספר הרישום של החברה הנמענת שמודפס בחשבונית גובר תמיד על כלל "עדכן עסק". אם יש סתירה, הכלל נרשם כ-overridden
  והמסמך מסומן לבדיקה.
- אין מחיקה פיזית של מסמך כספי על ידי כלל. "מחיקה" בממשק = העברה לארכיון (status archived + archived_at), עם רישום ביומן.
- כל הרשאה נאכפת ב-RLS ולא רק במסך: רק admin יוצר, עורך ומוחק כללים. finance_manager רואה אותם ואת ההיסטוריה.
- עיצוב: מערכת העיצוב הקיימת ב-finance.css (Almoni, נייבי #07293a לפעולות, אדום רק למה שדורש תשומת לב, RTL).
  לא להעתיק את הכחול של WellyBox ולא את האיורים שלהם. WellyBox הוא רפרנס לפונקציונליות ולסדר המסך בלבד.
- בסוף: npm run build עובר, ו-scripts/finance-e2e/run.mjs עובר במלואו כולל המבחנים החדשים. הוסף את המבחנים החדשים ל-run.mjs
  ועדכן את docs/finance/TESTING.md. אל תכתוב "עובד" על משהו שלא הרצת.
```

## פרומפט 1: מודל נתונים לכללים גנריים (תנאים ופעולות)

```
המטרה: להחליף את הכללים מבוססי ה-kind (11 סוגים קבועים) במבנה גנרי של "תנאים ← פעולות", כמו בצילומים 02 עד 04,
בלי לאבד את הכללים הקיימים.

שינויים ב-supabase/finance.sql (קטע חדש בסוף הקובץ, idempotent, בטוח להרצה חוזרת):

1. עמודות חדשות ב-fin_rules:
   - conditions jsonb not null default '[]'   -- מערך של { field, op, value }
   - match_mode text not null default 'all' check (match_mode in ('all','any'))   -- "וגם" / "או"
   - actions jsonb not null default '[]'      -- מערך של { type, value }
   - scope text not null default 'new' check (scope in ('new','new_and_pending'))
   - stop_processing boolean not null default false   -- אם הכלל חל, לא להמשיך לכללים בעדיפות נמוכה יותר
   - הוסף 'custom' לרשימת ה-kind המותרים. כלל חדש נשמר עם kind='custom'.

2. שדות התנאי (field) והאופרטורים שמותרים לכל אחד. אלה השדות מצילום 02, מותאמים לעמודות שלנו:
   | field (מזהה) | תווית בממשק | מקור הערך | סוג | אופרטורים |
   |---|---|---|---|---|
   | business      | עסק          | fin_documents.business_id     | ישות (חברה)  | equals, not_equals, is_empty |
   | sender        | שולח האימייל | email_from                    | טקסט          | contains, not_contains, equals, not_equals |
   | subject       | נושא האימייל | email_subject                 | טקסט          | contains, not_contains, equals, not_equals |
   | source        | מקור המסמך   | source (gmail/outlook/upload/camera/forward/whatsapp) + mailbox_id | רשימה | equals, not_equals |
   | supplier      | ספק          | supplier_id, וגם supplier_name לטקסט | ישות או טקסט | equals, not_equals, contains, not_contains |
   | category      | קטגוריה      | category_id                   | ישות          | equals, not_equals, is_empty |
   | paid          | סטטוס תשלום  | paid                          | בוליאני        | equals |
   | doc_type      | סוג מסמך     | doc_type                      | רשימה          | equals, not_equals |
   | content       | תוכן         | content_text (חדש, ראה 3)     | טקסט          | contains, not_contains |
   | amount        | סכום         | total_amount                  | מספר           | equals, not_equals, gt, gte, lt, lte, between |
   | project       | פרויקט       | project_id                    | ישות           | equals, not_equals, is_empty |
   | supplier_vat  | ח.פ ספק      | supplier_vat_id               | טקסט           | equals, is_empty |
   | recipient_vat | ח.פ הנמען    | extraction->>'customer_vat_id'| טקסט           | equals, is_empty |
   צילום 02 נחתך אחרי "סכום": ייתכן שיש שם עוד שדות. השלמתי פרויקט, ח.פ ספק וח.פ נמען כי בלעדיהם אי אפשר לבטא את כללי
   המפרט ("ח.פ הנמען ← חברה", "חסר ח.פ ← סימון").
   את הטבלה הזו כותבים פעם אחת, כקבוע משותף לשרת ולמסך: server/finance/rules-schema.js. הממשק מייבא אותו דרך קובץ
   shared, או שהקובץ נכתב כך ש-Vite וגם Node יכולים לייבא אותו. בלי שתי רשימות נפרדות.

3. content_text: עמודה חדשה ב-fin_documents (text). מוסיפים לסכמת החילוץ ב-server/finance/extract.js שדה full_text
   ("כל הטקסט המודפס במסמך, עד 6,000 תווים") ושומרים אותו ב-content_text. אם המקור מייל, מוסיפים גם את גוף המייל.
   החיפוש לא תלוי באותיות גדולות וקטנות, ומנרמל רווחים, גרש ומירכאות (׳ ' ״ ").

4. פעולות (actions.type), מצילום 04 ומההרחבות שלנו:
   | type | תווית | value | התנהגות |
   |---|---|---|---|
   | archive         | מחיקת המסמכים התואמים | – | status=archived ו-archived_at. לא מחיקה פיזית. בממשק נכתב "העברה לארכיון (מחיקה)" |
   | set_business    | עדכן עסק              | business_id | בכפוף לכלל ח.פ הנמען (ראה ההקשר המשותף) |
   | set_supplier    | עדכן ספק              | supplier_id | רק ספק בסטטוס active |
   | set_category    | עדכן קטגוריה          | category_id | רק קטגוריה פעילה |
   | set_status      | עדכן סטטוס            | review, rejected, duplicate | אסור approved או sent. כלל לא מאשר אף פעם |
   | set_project     | עדכן פרויקט           | project_id  | רק פרויקט של אותה חברה. אחרת: הצעה ואזהרה project_company |
   | set_paid        | עדכן סטטוס תשלום      | true/false  | |
   | flag            | סמן לבדיקה            | טקסט ההודעה | מוסיף issue ברמת warn עם הקוד rule_flag |
   | second_approval | דרוש אישור כפול       | – | מדליק requires_second_approval. הטריגר הקיים ימשיך לאכוף |

5. מיגרציה של הכללים הקיימים: כל כלל עם kind ישן מקבל conditions ו-actions שקולים. למשל supplier_category →
   [{field:'supplier',op:'equals',value:<supplier_id>}] ← [{type:'set_category',value:<category_id>}]. את ה-kind
   הישן משאירים, כדי שאפשר יהיה לחזור אחורה. מיגרציה idempotent: לא דורסת conditions שכבר קיימות.
   amount_flag עובר ל-amount gte ← flag. amount_approval עובר ל-amount gte ← second_approval.
   missing_vat_flag עובר ל-supplier_vat is_empty ← flag.

6. ולידציה במסד: פונקציה fin_rule_valid(conditions, actions) שבודקת שכל field ו-op מותרים לפי הטבלה, שיש לפחות
   תנאי אחד ופעולה אחת, ושאין set_status עם approved או sent. Check constraint או טריגר על fin_rules.

מבחני קבלה (להוסיף ל-run.mjs):
- R-MIG: אחרי הרצת finance.sql, כל כלל ישן מקבל conditions ו-actions תקינים, וההרצה השנייה לא משנה כלום.
- R-VAL: insert של כלל עם op לא חוקי, או עם set_status=approved, נכשל במסד (REST מחזיר 4xx).
- R-RLS: finance_manager מקבל 0 שורות ב-PATCH ל-fin_rules, וב-insert מקבל 4xx. admin מצליח.
```

## פרומפט 2: הפעלת הכללים בצנרת המסמכים

```
המטרה: ש-server/finance/assign.js יעריך את הכללים הגנריים מפרומפט 1, על כל מסמך חדש, בסדר עדיפות, ויתעד כל הפעלה.

1. מנוע הערכה טהור (בלי גישה למסד) ב-server/finance/rules-engine.js:
   evaluate(rule, docView) ← { matched, reasons[] }
   docView הוא אובייקט שטוח שבנוי מהמסמך ומהחילוץ: business, sender, subject, source, mailbox, supplier (id),
   supplier_name, category, paid, doc_type, content, amount, project, supplier_vat, recipient_vat.
   אופרטורים:
   - contains / not_contains: אחרי נרמול (lowercase, רווחים, גרשיים).
   - equals / not_equals: השוואה מדויקת. ישויות לפי id.
   - gt, gte, lt, lte, between: על ערך מוחלט של הסכום.
   - is_empty.
   - match_mode: all = כל התנאים. any = לפחות אחד.
   כתוב לו מבחני יחידה (node --test) על כל אופרטור, כולל עברית, ניקוד, גרשיים ורווחים כפולים.

2. השתלבות ב-assign():
   - הכללים נטענים לפי priority עולה, ורק enabled=true.
   - לכל כלל שמתאים, כל פעולה עוברת דרך consider() הקיים, עם ודאות 0.95. הודעה flag מוסיפה issue.
     archive ו-set_status משנים את fields.status, רק אם המסמך עוד לא אושר.
   - stop_processing: אחרי כלל שהתאים ויש לו stop_processing, לא מעריכים כללים בעדיפות נמוכה יותר.
   - סדר ההכרעה הקיים נשאר בדיוק כמו שהוא: ח.פ הנמען המודפס (1.0) גובר על set_business (0.95).
   - כל כלל שהתאים נרשם ב-fin_rule_hits עם outcome: applied, overridden, flagged או skipped_approved, ועם detail
     שמסביר למה (הטקסט שמופיע ב"היסטוריית הפעלות").
   - כלל שנכשל בהערכה, למשל ישות שנמחקה, נרשם עם outcome=error ולא עוצר את עיבוד המסמך.

3. scope:
   - 'new': רק מסמכים שנכנסים מעכשיו. זו ברירת המחדל, כמו "יופעל על כל מסמך חדש" בצילום 02.
   - 'new_and_pending': בשמירה, השרת מריץ את הכלל גם על המסמכים הקיימים בסטטוס processing, review או failed.
     פעולת שרת חדשה ב-server/finance.js:
     action:'rule-preview' { rule } ← מחזיר כמה מסמכים קיימים יתאימו, ודוגמה של עד 5, בלי לשנות כלום.
     action:'rule-apply' { rule_id } ← מריץ על הקיימים (admin בלבד), עם audit ועם fin_rule_hits.
     מסמך מאושר או מיוצא לא נוגעים בו אף פעם.

מבחני קבלה:
- R-ENG: מבחני היחידה של rules-engine עוברים.
- R-NEW: כלל "נושא האימייל מכיל 'statement' ← עדכן קטגוריה תקשורת". מייל חדש עם PDF ונושא "Your October statement"
  מקבל את הקטגוריה, ויש hit עם applied.
- R-PRIO: שני כללים סותרים על אותו מסמך. החל זה שבעדיפות גבוהה יותר. השני נרשם overridden.
- R-STOP: stop_processing מונע את הכלל שאחריו.
- R-VAT: כלל "ספק = Meta ← עדכן עסק קורקוס ביצוע" על חשבונית שבה מודפס ח.פ של קורקוס גרופ: העסק נשאר קורקוס גרופ,
  וה-hit הוא overridden.
- R-ARCH: כלל "סוג מסמך = הצעת מחיר ← מחיקה". המסמך מקבל status=archived ונשאר במסד, ובקובץ האחסון לא נוגעים.
- R-APPROVED: rule-apply על מסמך מאושר לא משנה אותו (skipped_approved).
```

## פרומפט 4: בונה הכללים, חלון "יצירת כלל" (צילומים 02 עד 04)
